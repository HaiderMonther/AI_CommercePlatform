# Architecture — AI Commerce Platform

> المصطلحات التقنية بالإنجليزية والشرح بالعربية.

## 1. نظرة عامة

المنصة ليست Chatbot، بل **نظام إدارة مبيعات وتجارة مدعوم بالذكاء الاصطناعي**.
المحادثة ليست الهدف، بل المدخل إلى دورة بيع كاملة.

```
        ┌──────────── قنوات التواصل ────────────┐
        │  WhatsApp    Instagram    Messenger   │
        └───────────────────┬───────────────────┘
                            │ Webhook (موقّع + idempotent)
                   ┌────────▼────────┐
                   │ Channels Module │  ChannelProvider abstraction
                   └────────┬────────┘
                            │ enqueue (BullMQ)
                   ┌────────▼────────────┐
                   │ Conversation Service│ ← Customer resolution
                   └────────┬────────────┘
                            │
                   ┌────────▼────────┐        ┌──────────────┐
                   │   AI Service    │───────▶│   AI Tools   │
                   │ intent + tools  │◀───────│ (allow-list) │
                   └────────┬────────┘        └──────┬───────┘
                            │                        │ يستدعي خدمات الأعمال فقط
              ┌─────────────┼────────────┐           │
              │             │            │     ┌─────▼──────────────────┐
        ┌─────▼─────┐ ┌─────▼─────┐ ┌────▼───┐ │ Products · Inventory   │
        │  Reply    │ │ Handover  │ │ Order  │ │ Customers · Orders     │
        │ (outbound)│ │ to human  │ │ create │ └────────────────────────┘
        └───────────┘ └───────────┘ └────┬───┘
                                         │
                              ┌──────────▼──────────┐
                              │ Inventory movement  │
                              │ Notification · WS   │
                              │ Audit · Usage       │
                              └──────────┬──────────┘
                                         │
                              ┌──────────▼──────────┐
                              │ Dashboard · Reports │
                              └─────────────────────┘
```

**المبدأ المركزي:** الذكاء الاصطناعي **لا يلمس قاعدة البيانات مباشرة**. يستدعي أدوات
(Tools) ذات عقد واضح، وكل أداة تمر عبر التحقق والصلاحيات ومنطق الأعمال نفسه الذي
يستخدمه الموظف البشري من لوحة التحكم. هذا يعني أن أي خلل في نموذج اللغة يبقى محصوراً
داخل حدود الأداة، ولا يتحول إلى كتابة عشوائية في البيانات.

## 2. تعدد الشركات (Multi-Tenancy)

### الاستراتيجية

**Shared database / shared schema** مع عمود تمييز `companyId`.

| البديل | لماذا لم نختره |
| --- | --- |
| قاعدة بيانات لكل شركة | تكلفة تشغيلية عالية، ومايكريشن على آلاف القواعد |
| Schema لكل شركة | نفس مشكلة المايكريشن + حدود Postgres على عدد الـschemas |
| **عمود companyId** | ✅ مايكريشن واحد، تقارير عبر الشركات ممكنة، تكلفة منخفضة |

المقايضة: العزل يصبح مسؤولية التطبيق لا قاعدة البيانات، لذلك نضع **ثلاث طبقات**:

### الطبقات الثلاث للعزل

```
1. JWT + Request Context
   الـtoken يحمل هوية المستخدم. عند كل طلب يُعاد تحميل المستخدم من قاعدة البيانات
   وتُقرأ الشركة من السجل نفسه — لا من جسم الـtoken. لذا لا ينفع تزوير claim.
   السياق محفوظ في AsyncLocalStorage (nestjs-cls) مع correlationId.

2. Prisma Client Extension  (src/common/prisma/tenant-prisma.provider.ts)
   كل استعلام على موديل مملوك للشركة يُحقن فيه companyId تلقائياً:
     - where  →  findUnique/First/Many · count · aggregate · groupBy
                 update · updateMany · delete · deleteMany
     - data   →  create · createMany · upsert
   تمرير companyId لشركة أخرى صراحةً يرفع CROSS_TENANT_ACCESS.
   حتى لو نسيت خدمة الفلتر، لا تصل إلى بيانات شركة أخرى.

3. مفاتيح فريدة على مستوى الشركة
   @@unique([companyId, sku]) · [companyId, slug] · [companyId, phone] · [companyId, email]
   فلا يتسبب تكرار SKU بين شركتين بأي تصادم.
```

`tenant-scope.ts` يفرض تصنيف **كل** موديل إما tenant-scoped أو exempt صراحةً،
واختبار `tenant-scope.spec.ts` يفشل إذا أضيف موديل جديد دون تصنيف — وهذه أسهل طريقة
لتسريب البيانات لولا هذا الاختبار.

### الاستثناءات المقصودة

| الموديل | السبب |
| --- | --- |
| `Permission`، `Plan` | بيانات مرجعية عامة على مستوى المنصة |
| `RolePermission` | محكوم بالشركة عبر الـRole الأب |
| `ProductImage` | محكوم عبر المنتج الأب |
| `RefreshToken` | محكوم عبر المستخدم، ويُقرأ قبل وجود سياق شركة |
| `WebhookEvent` | يصل قبل تحديد الشركة؛ تُربط بعد فك الـpayload |

### مدير المنصة

`User.isPlatformAdmin = true` مع `companyId = null`. لا سياق شركة، لذا لا يُفعّل حقن
الفلتر، ويملك صلاحيات `platform.*`. الفهرس الجزئي في المايكريشن يضمن تفرّد بريده،
لأن Postgres يعتبر NULL قيمة مميزة داخل المفتاح المركّب.

## 3. نموذج البيانات

28 جدولاً. المخطط الكامل في `apps/api/prisma/schema.prisma`.

```
Company 1─┬─* User *─1 Role *─* Permission
          ├─* Category 1─* Product 1─* ProductVariant
          │                  └─* ProductImage
          ├─* InventoryMovement  (سجل كل حركة مخزون)
          ├─* Customer 1─* CustomerIdentity   (هوية لكل منصة)
          │        └─* Conversation 1─* Message
          │                  └─* AiInteraction
          ├─* ChannelConnection 1─* Conversation
          ├─* Order 1─┬─* OrderItem
          │           └─* OrderStatusHistory
          ├─1 AiConfig
          ├─* Subscription *─1 Plan 1─* Invoice
          ├─* UsageRecord · Notification · AuditLog
          └─* WebhookEvent
```

### قرارات تصميمية

**`CustomerIdentity` بدل `platform`/`platformUserId` على الزبون**
الزبون الواحد يراسل التاجر من واتساب اليوم ومن إنستغرام غداً. لو خزّنّا المنصة على
الزبون لأنشأنا زبوناً مكرراً لكل قناة، ودمجهما لاحقاً يعني فقدان تاريخ الطلبات.
الجدول المنفصل يحل ذلك من البداية.

**`InventoryMovement` إلى جانب `Product.stock`**
الرقم المجرد لا يجيب "لماذا نقص المخزون؟". كل تغيير يُسجَّل مع الكمية قبله وبعده
ومرجعه (طلب، إرجاع، جرد)، فيصبح `stock` قابلاً لإعادة الاحتساب والتدقيق.

**`Decimal(14,3)` للمبالغ**
`Float` يُفقد الدقة في الجمع المتكرر. ثلاث خانات عشرية تغطي الدينار العراقي (بلا كسور
عملياً) والدولار (سنتان) معاً.

**`reservedStock` منفصل عن `stock`**
عند تجميع الطلب من المحادثة نحجز الكمية دون خصمها، حتى لا يبيع المساعد الذكي نفس
القطعة لزبونين في وقت واحد. المتاح للبيع = `stock - reservedStock`.

**كاتب واحد للمخزون**
لا تُحدَّث `stock` أو `reservedStock` من أي خدمة مباشرة. كل تغيير يمر عبر
`InventoryService.recordMovement` الذي يقفل الصف، يتحقق من النتيجة، ويكتب حركة
`InventoryMovement` في المعاملة نفسها. الترتيب ثابت: يُقفل المنتج الأب أولاً ثم
المتغير — لأن مجموع المنتج يُعاد احتسابه من متغيراته بعد التحديث، وبدون قفل الأب
تقرأ حركتان متزامنتان بيانات لم تُثبَّت بعد فتضيع إحدى الكتابتين. وهذا الترتيب
الموحّد يمنع الـdeadlock أيضاً.

**`ADJUSTMENT` يضبط قيمة مطلقة**
باقي الأنواع تُزيح الكمية بمقدار، أما الجرد فيصحّح السجل إلى ما وُجد فعلياً على الرف.

**الحذف الناعم يحرّر المفتاح الطبيعي**
عند حذف مستخدم يُضاف لاحقة للبريد المخزّن، فيبقى السجل للتدقيق ويمكن دعوة الشخص
نفسه لاحقاً دون تصادم مع `@@unique([companyId, email])`.

### الفهارس

مبنية على أنماط القراءة الفعلية لا على التخمين:

```
(companyId, status, createdAt)   قوائم الطلبات والمحادثات المفلترة
(companyId, createdAt)           الترقيم الزمني الافتراضي لكل قائمة
(conversationId, createdAt)      تحميل رسائل محادثة بالترتيب
(referenceType, referenceId)     تتبع حركة مخزون إلى مصدرها
(channel, externalEventId)       فريد — يمنع معالجة نفس الـwebhook مرتين
```

## 5. الأمان

### المصادقة

| القرار | السبب |
| --- | --- |
| **Argon2id** لكلمات المرور | مقاوم للذاكرة، يجعل كسر جدول hashes مسرّب غير عملي على GPU |
| **Access token قصير (15د)** | يقلّص نافذة استغلال أي رمز مسرّب |
| **Refresh token مخزّن بصيغة hash** | تسريب قاعدة البيانات لا يعطي رموزاً صالحة |
| **تدوير + كشف إعادة الاستخدام** | تقديم رمز مستهلك يُلغي عائلة الجلسة كاملة — سلوك السارق المعتاد |
| **الصلاحيات تُحلّ عند كل طلب** | سحب دور يسري فوراً، لا عند انتهاء الـtoken |
| **رسالة خطأ موحّدة عند الفشل** | لا يمكن استخدام نقطة الدخول لمعرفة البُرد المسجّلة |

### الصلاحيات

RBAC بصيغة `<group>.<action>` في جدول كتالوج، فإضافة قدرة جديدة لا تتطلب تغيير المخطط.
خمسة أدوار افتراضية غير قابلة للتعديل لكل شركة، والتوسعة عبر أدوار مخصصة.

حواجز تمنع الشركة من إقفال نفسها أو التسرب:
- لا يمكن تنزيل أو إيقاف أو حذف آخر مالك فعّال
- لا يمكن للمستخدم إيقاف أو حذف حسابه
- إسناد دور من شركة أخرى يفشل كـ`ROLE_NOT_FOUND` لا كـ`FORBIDDEN` (لا نكشف وجوده)
- قراءة سجل من شركة أخرى تُرجع 404 لا 403، فلا تُستخدم المعرفات للاستكشاف

### طبقات الحماية الأخرى

| التهديد | الإجراء |
| --- | --- |
| SQL Injection | Prisma بمعاملات مُهيّأة؛ لا استعلام نصي مبني من مدخلات |
| Mass assignment | `ValidationPipe` بـ`forbidNonWhitelisted` — أي حقل غير معرّف يرفض الطلب |
| Broken access control | حارس صلاحيات عام + `@RequirePermissions` على كل نقطة |
| Cross-tenant access | الطبقات الثلاث في القسم 2 + اختبارات E2E مخصصة |
| Brute force | Throttler: 10 محاولات/دقيقة على نقاط المصادقة |
| Webhook spoofing | التحقق من التوقيع + `@@unique([channel, externalEventId])` للـidempotency |
| تسريب الأسرار | كل الأسرار من البيئة؛ بيانات القنوات مشفّرة AES-256-GCM؛ تنقيح تلقائي في سجل التدقيق |
| رؤوس HTTP | Helmet + CORS بقائمة مصادر صريحة |

### سجل التدقيق

كل عملية حساسة تُسجَّل: المنفّذ، العملية، الكيان، القيمة قبل وبعد، الـIP،
و`correlationId` الذي يربطها بسطر السجل في الـAPI. الأسرار تُنقّح قبل التخزين،
وفشل كتابة السجل لا يُسقط العملية التجارية لكنه يُسجَّل كخطأ.

## 6. معمارية الذكاء الاصطناعي (المرحلة 6)

```
رسالة الزبون
     │
     ▼
Conversation Service ── يبني السياق: الشركة، الزبون، آخر الرسائل، AiConfig
     │
     ▼
AI Service ─────────── يحدد النية ويختار الأداة
     │
     ▼
Tool Layer (allow-list صارمة)
     ├── searchProducts        ├── createOrder
     ├── getProductDetails     ├── getCustomerOrders
     ├── checkStock            ├── getCompanyInformation
     ├── getProductPrice       └── handoverToHuman
     │
     ▼  كل أداة: Input Schema → Validation → Authorization → Business Logic → Error Handling
خدمات الأعمال ──▶ قاعدة البيانات
```

**قيود مقصودة**

1. الأداة **لا تستقبل `companyId` من النموذج**؛ يأتي من سياق الطلب. فلا يستطيع
   prompt injection توجيه الاستعلام إلى شركة أخرى.
2. لا توجد أداة عامة للكتابة. `createOrder` هي نقطة الكتابة الوحيدة، وتتطلب حقولاً
   مكتملة ومؤكَّدة (الاسم، الهاتف، العنوان، المنتج، الكمية، طريقة الدفع).
3. كل استدعاء يُسجَّل في `AiInteraction` مع النية والرموز والزمن — للتكلفة والتشخيص.
4. `AiConfig` لكل شركة: اسم النشاط، النبرة، اللغة (عربية عراقية افتراضاً)، العملة،
   ساعات العمل، سياسات الإرجاع والتوصيل، طرق الدفع، وتعليمات مخصصة.

**التحويل لموظف بشري**
عبر كلمات مفتاحية، أو طلب صريح من الزبون، أو فشل الأداة، أو انخفاض ثقة النموذج.
عندها `Conversation.mode = HUMAN`، ويتوقف الرد الآلي، ويصل إشعار فوري عبر WebSocket
إلى لوحة الموظف. الموظف يستطيع التدخل في أي محادثة بأي وقت دون انتظار التحويل.

## 7. المعالجة غير المتزامنة

الـWebhook يجب أن يرد خلال ثوانٍ وإلا أعادت Meta الإرسال. لذلك:

```
Webhook → التحقق من التوقيع → تخزين WebhookEvent → 200 OK فوراً
                                      │
                                      ▼ (BullMQ على Redis)
                        معالجة: زبون → محادثة → رسالة → AI → رد
```

الطوابير المخططة: `webhooks`، `ai-processing`، `outbound-messages`، `notifications`،
`reports`. مع إعادة محاولة أسّية و dead-letter queue.

## 8. الزمن الحقيقي

WebSocket (Socket.IO) على `/api/socket.io`، خلف نفس بروكسي الـAPI.

```
company:{id}                 كل أعضاء الشركة (إشعارات المراحل القادمة)
company:{id}:conversations   من يملك conversations.read ← conversation:updated
conversation:{id}            بالانضمام الصريح بعد تحقق الشركة ← message:created
user:{id}                    إشعارات شخصية
```

- **المصادقة في الـhandshake** بنفس الـaccess token ونفس حل الـprincipal في REST. الحراس
  العامة لا تعمل على الـsockets، لذا البوابة `@Public` و`@SkipThrottle` وتتحقق بنفسها.
- **الغرف تُشتق من سجل المستخدم** لا من اسم يرسله العميل. الانضمام لمحادثة يمر باستعلام
  مقيّد بشركة الـsocket، فمعرف شركة أخرى يبدو كمعرف غير موجود.
- **الصلاحيات تُلتقط عند الاتصال**، والخادم يغلق الـsocket عند انتهاء الرمز، فسحب دور
  يسري خلال عمر رمز واحد (15 دقيقة).
- **البث بعد الـcommit ولا يُفشل العملية**: رسالة محفوظة لا تُرفض لأن البث تعثّر. العميل
  يعيد جلب القائمة بعد كل إعادة اتصال لأن الأحداث الفائتة لا تُعاد.
- **Redis adapter** يوصل الحدث لـsockets متصلة بأي نسخة من الـAPI. بدون Redis تعمل نسخة
  واحدة بشكل كامل مع تحذير في السجل.

### حل هوية المرسل

الرسالة الواردة (من webhooks المرحلة 5) تمر بـ`MessagesService.recordInbound`:

```
externalId مكرر؟ ──نعم──▶ تُعاد الرسالة الأصلية (idempotent)
      │ لا
CustomerIdentity (قناة + معرف المنصة)؟ ──▶ الزبون نفسه
      │ لا
زبون بنفس الهاتف؟ ──▶ يُربط به حساب القناة الجديد
      │ لا
زبون جديد + هوية
      │
محادثة غير مغلقة لهذا الزبون على القناة؟ ──▶ تُستكمل (وتُعاد فتحها)، وإلا تُنشأ
```

السباق بين webhookين لنفس المرسل الجديد يحسمه المفتاح الفريد على الهوية وعلى
`(companyId, externalId)`، ويُعاد قراءة ما كتبه الفائز.

```
├── stores/       Pinia: auth · ui
├── types/        عقود الـAPI
└── views/        شاشات مقسّمة حسب المجال
```

- **RTL وعربية افتراضاً**، مع بقاء الأرقام لاتينية (`ar-IQ-u-nu-latn`) لأن الأرقام
  العربية-الهندية تكسر محاذاة الجداول ولا تطابق الفواتير المطبوعة.
- **الصلاحيات في `meta.permissions`** تخفي ما لا يستطيع المستخدم فعله؛ الـAPI يبقى
  نقطة الفرض الفعلية.
- **تجديد الجلسة موحّد**: طلب تجديد واحد مشترك بين كل الطلبات المعلّقة، وإلا لأطلقت
  صفحة واحدة خمسة تجديدات متزامنة وأشعلت كشف إعادة استخدام الرمز.
- **حالات واضحة** لكل شاشة: تحميل (skeleton)، فارغ، خطأ مع `correlationId`.

## 10. النشر

```
Internet → nginx (web) ──/──▶ ملفات ثابتة
                        └─/api─▶ api:3000 (NestJS)
                                    ├──▶ postgres:5432
                                    └──▶ redis:6379
```

خدمة `migrate` منفصلة تطبّق المايكريشن وبيانات النظام ثم تنتهي، فلا تتسابق نسخ
الـAPI على المايكريشن عند التوسّع الأفقي. التفاصيل في [DEPLOYMENT.md](DEPLOYMENT.md).
